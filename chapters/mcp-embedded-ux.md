MCP（Model Context Protocol）是讓 AI 模型接上外部工具和資料的一套標準。有了它，模型可以查地圖、讀郵件、下訂單。技術上這很漂亮，但我一直覺得它的使用者體驗很怪。

現在主流的 MCP 用法，大多綁在 Cursor 或 Chatwise 這類專門工具上。對工程師沒問題，我自己就用過一個 MCP，把本機正在除錯的頁面元件、log 和截圖直接傳回 Cursor，很好用。但那是因為我本來就整天待在 Cursor 裡。

換成一般人就不是這樣了。舉個例子：申請簽證要做一份行程單。傳統做法是開瀏覽器和手機查地圖、查景點、查機票飯店和火車訂單，再開 Excel 整理成表。有了 MCP，理論上 AI 可以把這些都接起來。但很難想像要一般使用者先下載 Cursor 或 Chatwise、做一堆設定，才能完成這件事。

這篇寫給在做 AI 產品、或在想 MCP 該怎麼落地的人。我的看法是：**問題不在 MCP 能接什麼，而在它用什麼形態出現在使用者面前。**

## 聊天式 MCP 的四個問題

**1. 打斷工作。** 像 Siri、ChatGPT 這種對話模式，使用者得停下手上的事，一句一句打字或講話，再等它回應。做行程單就要一步步說「查上海到東京的機票」「加一間飯店」。這樣效率低，還打斷思路，跟傳統的瀏覽器加 Excel 比沒有明顯優勢。

**2. 門檻高。** 要下載專門工具、設定環境、輸入專業指令。對一般使用者太麻煩，做不到打開就用。

**3. 太被動。** 對話式 MCP 通常是你問一句它答一句，不會預判你的意圖，也不會主動把地圖、訂單這些不同來源的資料整合起來。使用者得自己拆任務，一步步引導它。本質上是人在遷就機器。

**4. 聊天框裝不下結構化結果。** 行程單是表格，不是一段對話。表格和圖表硬塞進對話框會很零散，之後要改也不方便。

聊天形態適合探索性的對話和發散想法。但碰到多步驟、要多個工具協同的具體任務，就顯得笨拙。

## 理想形態：系統級的「隱形助手」

我想像中的 MCP 應該長這樣：

- **觸發方式**：融進裝置本身。電腦上按快捷鍵（例如 Opt + Space）或按住空白鍵講話，手機上用上滑之類的手勢。不需要特地打開某個 App。
- **呈現方式**：不要全螢幕介面。一個浮動小視窗或狀態列外掛，需要時短暫出現，做完發通知，結果直接放進剪貼簿或資料夾。你原本在用的瀏覽器、Excel 不會被打斷。
- **運作方式**：關鍵是在背景自動跑。主動調用系統資源（地圖、郵件、行事曆）或外部 API（機票、飯店訂單），自己整理資料、排版，輸出結構化結果。使用者只下指令，不用手動設定。
- **入口位置**：不是一個獨立 App，而是直接內建在系統層。有點像 Spotlight 或 Siri，但更聰明，也更以任務為導向。

回到行程單的例子：理想的流程是我在看機票網頁時按一下快捷鍵，說「幫我把這趟東京行程整理成簽證用的行程單」，然後繼續做別的事。幾分鐘後收到通知，一份排好的表格已經在資料夾裡。

## B 端比 C 端更早落地

一般消費者（C 端）對這種工具的接受門檻還是偏高，短期內價值有限。要等到「隱形助手」這種系統級入口出現，C 端才會普及。

企業（B 端）的機會明確得多。IT 部門先把規則和 API 串接設定好，行政或商旅部門的員工就能直接用自然語言觸發整套流程。這省下的是實際的人力成本：一個行政職位一年的成本大約 10–20 萬，商旅機構能省的更多。所以 B 端現在就可以靠嵌進 ERP 或商旅系統的方式落地，不用等系統入口。

## 小結

我認為 MCP 最好的形態是系統級的隱形助手：嵌在裝置裡，用快捷鍵或語音觸發，用浮動小視窗呈現，在背景跑完資料、輸出結構化結果，不打斷你手上的事。B 端則可以嵌進 ERP 或商旅系統，由 IT 預先設好規則，讓員工直接用自然語言觸發。
