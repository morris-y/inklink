用 Claude Code 久了，會開始在意 token。訂閱方案有額度上限，跑得越兇，越早撞到「請稍後再試」。

所以當我看到 Microsoft 開源的 [TokenEconomizer](https://github.com/microsoft/TokenEconomizer)，說它能從過去的 session 學習、幫 coding agent 省 token，我第一個反應是：裝起來試試。

第二個反應是：先別急著相信。

這篇記錄我怎麼試、怎麼量，以及為什麼 6 天後把它拆了。如果你也在考慮裝某個「省 token」或「讓 agent 變聰明」的外掛，這套量法可以直接拿去用。

## 它聲稱怎麼省

TokenEconomizer 是一個 Claude Code 外掛。它讀你過去的 session 紀錄，學出三種東西：

1. **microskills**：把這個 repo 的環境事實，例如測試指令、重要路徑，在每個 session 開頭先告訴 agent，省掉它重新摸索。
2. **toolprune**：找出你從來沒用過的工具，提議把它們關掉。每次請求帶的工具說明變短，token 就少。
3. **loopguard**：發現 agent 在原地打轉時提醒它換方法，避免白燒好幾輪。

聽起來都合理。問題是：在我的 repo、我的用法下，它真的有省嗎？

## 試用前先寫下「怎樣算成功」

我有一個習慣：任何想試的工具，先登記成一個有期限的實驗，寫下假設和量法，到期看數據決定留下或回滾。（這套做法我在[〈Claude Code skill 怎麼評估要不要留〉](/writing/ai-tool-experiment-board-zh)寫過。）

這次的假設是：

> 在我的個人網站 repo 裡省下 token，**而且**成功率不下降。

兩個條件都要成立才採用。只省 token 但 agent 變笨，不值得；成功率一樣但沒省，等於白付開銷。

期限 7 天。範圍只裝在一個 repo，不裝全域，出事也只影響一個地方。

## 第一份數據：真實使用 6 天

外掛自己有一個 `te status` 指令，會回報學到什麼、花了多少。我讓排程每天記一次：

| 日期 | 累積 session | 外掛自己的開銷 |
|---|---|---|
| 11/7 | 2 | 0（0.0%） |
| 11/8 | 2 | 40.4k（0.4%） |
| 11/9 | 9 | 410.4k（0.8%） |
| 11/10 | 11 | 590.7k（1.2%） |

6 天、11 個 session 之後：

- microskills 注入了 **0** 條事實。它沒有學出任何東西可以提前告訴 agent。
- toolprune 列出 18 個沒用過的工具，但只是「提議」。不套用就省不到。
- loopguard 在 216 輪裡只提醒過 1 次。

唯一確定的效果，是它自己的開銷一路從 0% 爬到 1.2%。

但真實使用的數據有個問題：每天做的事不一樣，沒辦法直接比「有裝」和「沒裝」。所以到期前我又做了一次對照測試。

## 第二份數據：30 次 A/B 測試

我用一個自己寫的小工具 `agent-ab`，同一個任務跑兩組 Claude Code：

- **對照組**：外掛關掉。
- **實驗組**：外掛打開。

其他條件完全一樣：同一個模型（Sonnet）、同一份 repo 快照、每次最多 15 輪。每次執行都從乾淨的副本開始，互不影響。

我挑了三個在這個 repo 裡真的會做的小任務，每個任務都配一個檢查：沒改對就失敗，改對才通過。每組各跑 5 次，總共 30 次。

| 任務 | 成功（關／開） | 平均 token（關／開） | 差異 |
|---|---|---|---|
| 在驗證模組加一個函式 | 5/5 ／ 5/5 | 146.7k ／ 156.0k | +6% |
| 列出引用某個模組的檔案 | 5/5 ／ 5/5 | 83.7k ／ 127.6k | +52% |
| 加一個常數並換掉寫死的字串 | 5/5 ／ 5/5 | 129.8k ／ 130.0k | 0% |

成功率 15/15 對 15/15，外掛沒有讓 agent 變笨。

但 token 沒有一題變少。第二題甚至多了 52%：開外掛的 5 次裡，有 3 次多跑了一輪。速度也慢了 1 到 3 秒，跟它每次工具呼叫多約 70 毫秒的 hook 開銷對得上。

## 為什麼拆掉，而不是再給它一點時間

拆掉的理由很簡單：假設要兩個條件同時成立，現在只成立一個。

我考慮過延長試用，最後沒有，因為延長只是等待。它省 token 的三條路裡：

- microskills 6 天沒學出東西，我看不出再等一週會不同；
- loopguard 幾乎沒觸發；
- 唯一有實際效果的 toolprune，要我手動改設定、關掉一批工具。

如果要改設定，我可以自己關，不需要一個常駐的外掛幫我「提議」。

也要說清楚這次測不到的地方。三個任務都很短，2 到 6 輪就做完。TokenEconomizer 號稱在長 session、累積很多歷史之後才省得多，這次 A/B 沒有測到那種情況。所以這不是「這個外掛沒用」的結論，而是「在我的用法下，6 天內沒有看到它省任何東西」。

## 可以帶走的做法

比起這個外掛本身，我覺得更值得留下的是這套量法：

1. **先寫假設和成功條件**，而且至少包含「省了什麼」和「沒變差」兩個方向。
2. **只裝在一個地方**，期限寫死，到期一定要判定：採用、延長或移除。
3. **讓工具自己回報數字**，每天記一次，不靠感覺。
4. **到期前做一次對照測試**：同一個任務、只差一個開關、每組至少 5 次，搭配「沒做對就失敗」的檢查。

這次整個 A/B 用的是訂閱額度，30 次按 API 定價換算大約 4.4 美元，跑了不到 10 分鐘。比起讓一個外掛無聲地多吃 1.2% 的 token，這個成本很划算。
