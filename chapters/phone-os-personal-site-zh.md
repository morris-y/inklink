打開 [morrisshyang.com](https://morrisshyang.com)，你看到的不是一般的個人網站，而是一支 iPhone：要先滑開鎖定畫面，主畫面上有 Dock、資料夾、小工具，點 App 會從圖示放大打開，從底部往上滑可以回主畫面或叫出多工畫面。

我想要的是：大家一進到首頁，就看到很多跟我有關的 App。有的是我開發的產品，有的是我日常真的在用、也可以直接點開的東西，像我會做的菜、我的香水櫃，同時也有我的介紹和外部連結。

這個網站從 2026 年 6 月的作品集，變成 macOS 風格的桌面，11 月再變成現在的手機介面。到 11 月 16 日，repo 已經超過 350 個 commit、100 個 PR，大部分是我指揮 AI coding agent 寫的。這篇整理過程中真的踩到的坑，每一條都附 PR 編號，有量測的就附數字。

先講技術選型：Next.js 15、Tailwind、手勢和動畫用 Motion。我找過能直接拿來改的開源專案，結論是沒有值得 fork 的。最接近的 ryOS 是 AGPL 授權，意思是放到網路上提供服務，就得公開整個網站的原始碼；它又是 macOS 風格，所以我只參考思路，手機外殼自己寫。Apple 的字型、桌布和 SF Symbols 也都不能用。

## 坑 1：建置隨機失敗，「重跑就過」害我多失敗了兩次

2026-11-08 這天，Vercel 建置失敗了三次，錯誤都一樣。前兩次重新部署就過了，我們當成偶發。第三次一口氣卡住 8 個已經合併的 PR，網站停在舊版本，才有人去讀 log。

原因是 `next/font/google`：建置時它會去 Google Fonts 抓字型。大約 60 次裡有 1 次，Google 回傳一個沒有副檔名的網址，網址裡的 `&` 會讓 Next.js 的 Turbopack 解析失敗。這是 Next.js 上游的 bug（[vercel/next.js#99114](https://github.com/vercel/next.js/issues/99114)）。我們每次建置要抓 6 個字型，當天又部署了約 25 次，等於抽了一百多次獎。

修法是所有字型都自己託管（[PR #37](https://github.com/morris-y/Morris/pull/37)）：Geist 用官方套件，其他字型改用 Fontsource 的檔案，透過 `next/font/local` 載入。驗證方式是故意讓 Google Fonts 連不上：修之前建置失敗，修之後 54 頁全部通過。

學到的是：「重跑就過了」不等於沒事，第一次失敗就該讀 log。

## 坑 2：為了省建置額度，把真的程式改動也略過了

Vercel 有一個「略過建置」設定。我加了一條規則：只改文件就不建置，省額度（[PR #19](https://github.com/morris-y/Morris/pull/19)）。結果 11 月 10 日，一個手機版的修正沒有上線，部署紀錄寫著「Ignored Build Step」。

問題在規則只比較「最後一個 commit」。一次合併好幾個 PR 時，最後一個 commit 剛好只改了文件，規則就判斷整批都不用建置，把前面的程式改動一起略過。

[PR #57](https://github.com/morris-y/Morris/pull/57) 改成和「上一次成功部署的 commit」比較。這類優化要比的是「上次部署到現在改了什麼」，不是「上一個 commit 改了什麼」。

## 坑 3：放手那一刻，動畫凍結 1 秒

從 App 底部往上滑回主畫面時，比真的 iPhone 卡很多，放手那一刻畫面會凍住。我原本猜是 React 重繪太多次。

量測之後才發現猜錯了（[PR #79](https://github.com/morris-y/Morris/pull/79)，Chrome 4 倍 CPU 降速模擬）。手指移動時的工作量其實正常，兇手是放手時做的一件事：為了讓多工畫面的卡片顯示 App 的樣子，程式會把整個 App 截成圖。這一步會把主執行緒卡住 1081 毫秒。

修法是把截圖移到 App 剛打開、閒置的時候做，同時讓視窗的 X、Y 都 1:1 跟著手指，放手時再用距離加速度決定去哪裡。同一支量測腳本下，最差的一個 frame 從 751 毫秒降到 40–84 毫秒，超過 50 毫秒的長任務從 2 個變成 0 個。

代價是多工畫面的卡片顯示的是「App 剛打開時」的樣子，不是你離開時捲到的位置。在書櫃 App 上，即使只在離開時補截一次，也會凍結 1.4 秒，因為每張封面都要嵌進圖裡。我選擇接受這個代價。

## 坑 4：玻璃效果，iPhone 上的 Safari 不支援

iOS 的 Dock 和資料夾是半透明的「玻璃」，背後的桌布會被折射扭曲。網路上有現成的函式庫，例如 `liquid-glass-react`，但它們靠 CSS 的 `backdrop-filter` 裡放 SVG filter，而 Safari 會忽略這個用法（WebKit bug 245510）。在 iPhone 上，完全看不到折射。

我的桌布是一張靜態圖，所以換個做法（[PR #91](https://github.com/morris-y/Morris/pull/91)）：整個畫面放一個 WebGL canvas，把桌布的副本照光的折射公式扭曲，畫在每個玻璃元素的位置。只有元素移動時才重畫；瀏覽器不支援 WebGL2 或出錯時，自動退回 CSS 版本的玻璃。做法參考了 MIT 授權的 liquid-glass-studio。

「像不像真的 iOS」是主觀的，參數一直被推翻：先調得更霧，又覺得太乳白，再改回去。後來的做法是做一張對比板，把三個版本疊在同一張真實桌布上，旁邊放 iOS 的截圖，一次選定（[PR #89](https://github.com/morris-y/Morris/pull/89)）。比來回改參數快很多。

## 坑 5：`scrollIntoView` 把整支手機往上推

書櫃 App 裡有一本本可以翻頁的書。打開目錄再關掉書，整個主畫面會被往上推，底部出現一條黑帶。

原因是目錄用了 `scrollIntoView` 讓目前章節出現在畫面上。它不只捲動目錄，還會捲動所有能捲的外層，連手機外殼都被捲了 72 像素（[PR #97](https://github.com/morris-y/Morris/pull/97)）。在有固定外殼的介面裡，這個 API 很危險。改成只捲動目錄清單本身。

同一個 PR 也處理了內容超出頁面的問題：改成在真實頁面大小下先量文字、再切頁，不靠捲動。驗證用窮舉而不是抽樣：25 本書、3 種螢幕尺寸、一般和全螢幕兩種模式，沒有任何一頁超出；畫面上的字數和原文一致，沒有掉字。

## 坑 6：私人頁面在正式站上對所有人公開

網站有幾個私人區域，例如實驗室和我的廚房後台。原本的設計是「家裡的 IP 直接放行，其他人要密碼」。11 月我發現，正式站上這幾頁對外面的人也是打開的（[PR #50](https://github.com/morris-y/Morris/pull/50)）。

更麻煩的是，預覽環境測不出來：IP 白名單這個設定只放在正式站，預覽站沒有，所以預覽站一律要求密碼，看起來一切正常。

修法是拿掉 IP 白名單，每個區域都要密碼或記住裝置的 cookie。PR 附了新舊對照：同一個 IP、沒有憑證，舊版放行，新版擋下。最終的證明是上線後，用沒有憑證的請求打這幾頁，必須回 401。

只在正式站生效的設定，等於預覽階段無法驗證。上線後一定要用「什麼憑證都沒有」的請求實測一次。

## 坑 7：多個 AI agent 同時改一個 repo

這個網站常常同時有好幾個 agent 在做不同功能。出過的事：

1. **主分支被留在功能分支上。** 某個 agent 做完沒切回來，下一個 agent 在錯的分支上繼續做。
2. **寫在提示詞裡的規則，agent 不一定照做。** 後來改成用 hook 強制：每個 agent 都要在自己的 git worktree 裡工作，不准自己合併 PR、不准直接部署正式站。合併改成排程每天跑一次。能用程式擋的，就不要靠提示詞。
3. **一個 PR 默默刪掉另一個 PR 的功能。** 密碼頁的 PR（[#83](https://github.com/morris-y/Morris/pull/83)）建在舊的程式碼上，會把剛完成的天氣小工具和 App 資料庫刪掉。GitHub 顯示沒有衝突、CI 全綠、它自己的測試也過。是先試著依序合併才發現的。現在合併腳本會在「刪掉最近新增的檔案」時停下來寄信給我，但它抓不到「改內容」造成的還原，所以標記可以合併前，還是要看一眼改了哪些檔案。
4. **被中斷的指令可能已經生效。** 我中斷過一個合併指令，工具回報「沒執行」，實際上合併已經推上去、也部署了。從此中斷之後，一律先查 git 紀錄和部署列表再下結論。
5. **一次失敗的部署會卡住一整批 PR。** 這是每天批次合併的代價，也是好處：修好之後，一次部署就把 8 個 PR 和修正一起送上線。

## 還沒在真機上驗證的部分

桌面瀏覽器模擬不了「加到主畫面」之後的全螢幕模式，也模擬不了 iOS 底部的系統橫條。底部手勢會不會和系統的回主畫面手勢打架、鍵盤彈出時底部的黑條，相關 PR 都寫明「要真機驗證」。頁面指示點偶爾不切換的問題，在桌面 Chromium 上重現不了，[PR #98](https://github.com/morris-y/Morris/pull/98) 修掉的是可疑的程式路徑，不是確認過的根因。

## 結論

做一個像 iPhone 的網站，最難的不是畫得像，而是「摸起來像」：手勢跟手、放手不卡、玻璃在 Safari 上也看得到。這些全部靠量測才找得到兇手，用猜的幾乎都猜錯。

另一半的坑和介面無關，是流程：重跑就過的錯誤、只在正式站生效的設定、彼此看不到的 agent。我的做法是把檢查放進流程和程式裡，每個 PR 寫清楚量了什麼、還有什麼沒驗證。「沒驗證」寫出來，比寫「應該可以」有用得多。
